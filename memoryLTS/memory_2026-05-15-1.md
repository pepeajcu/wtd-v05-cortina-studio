# Sesion 2026-05-15 #1 — Decision sobre `reels_selected` en home-singleton

## Contexto previo

Durante la validacion manual de Fase 3.6 (fetchers contra CMS real) se detecto que `reels_selected` venia como string literal `"reels_selected"`. La spec `proposal.md §4.4` lo describia como "Relacion 1→N a CPT `proyecto`", pero al revisar el plugin `cortinastudio-wpgraphql-bridge` se confirmo que solo soporta dos tipos de campo: `scalar` (string via `get_post_meta`) y `repeater` (JSON string del array de post_meta). No hay resolver para Relaciones JetEngine reales.

## Decision tomada

**`reels_selected` se implementa como Repeater con un unico sub-campo `id` tipo Posts (selector de post nativo de JetEngine), filtrado al CPT `proyecto`.** No se usa la feature "Relations" de Crocoblock.

**Por que:**
- Las **Relaciones JetEngine** (Crocoblock → Relations → New Relation) viven en la tabla custom `jet_engine_relations`, no en `wp_postmeta`. El plugin bridge actual (`csb_scalar_resolver` / `csb_repeater_resolver`) lee con `get_post_meta($post->databaseId, $meta_key, true)`, asi que no las ve.
- Un meta field tipo **Posts** dentro de un Repeater SI se guarda en `post_meta` como parte del array del repeater, y JetEngine al serializarlo deja la key con el nombre literal del sub-campo (`id`).
- Shape resultante en GraphQL: `"{\"item-0\":{\"id\":\"15\"},\"item-1\":{\"id\":\"23\"}}"` — coincide con `reelSelectedSchema` (`{slug?, id?}` con `.passthrough()`) ya definido en `lib/wordpress/getHome.ts`, sin tocar codigo del fetcher.

**Como aplicar en JetEngine:**
1. CPT `home-singleton` → Meta Fields → editar/crear `reels_selected`.
2. Type: Repeater.
3. Repeater Fields: 1 sub-campo con Name literal `id` (no `reels_selected_id` ni prefijo), Type **Posts**, Post Type `proyecto`, Allow multiple **NO**.
4. Guardar el meta field, luego editar el post home-singleton para agregar 3-5 items eligiendo proyectos.
5. Tras guardar, invalidar cache de Next con POST a `/api/revalidate?secret=...` body `{"tag":"wp:home"}`.

## Nota arquitectonica

Esto NO bloquea soportar Relaciones JetEngine reales en el futuro. Si algun cliente requiere N→N con metadata por enlace (ej. orden, peso, fecha de promocion ligada al enlace y no al post), habria que:

- Extender `cortinastudio-wpgraphql-bridge.php` con un tercer tipo de field en `bridge-fields.json` (`"relation"`), que reciba el `relation_id` de JetEngine y resuelva via la API de JetEngine Relations (`jet_engine()->relations->...`) o lectura directa de `wp_jet_engine_relations`.
- Subir version del plugin (`CSB_VERSION`) y deployarlo a todos los clientes.

Para Cortina Studio no es necesario hoy: el repeater + sub-campo Posts cubre el caso "lista ordenada de proyectos destacados" sin metadata adicional por enlace.
