# Sesion 2026-05-13 #1 — Refactor de contexto a Skills + sistema LTS

## Contexto previo

Repo de la "fabrica de sitios premium" (Next.js 14 + WordPress headless). Cliente actual ocupando los slots: Cortina Studio. Antes del refactor:

- `CLAUDE.md` era un indice (~75 lineas) que apuntaba a `AGENTS.md`.
- `AGENTS.md` era un manual de ~1.700 lineas (21 secciones + apendice) cargado en cada sesion.
- No habia separacion explicita entre "motor de fabrica" y "configuracion del cliente Cortina Studio".
- No existia memoria entre sesiones — cada conversacion arrancaba en frio.
- Las skills de diseno de terceros vivian en `.claude/skills/taste-design/` y `.opencode/skills/taste-design/` pero nadie las referenciaba explicitamente.

## Que se hizo

### Fase 1 — Spec Driven Development
- Creada carpeta `docs/specs/refactor-contexto/`.
- `proposal.md`: diseno modular, principios, mapeo seccion-por-seccion AGENTS.md → destino, separacion fabrica vs cliente, beneficios y riesgos.
- `tasks.md`: checklist verificable de cada paso del refactor.

### Fase 2 — Refactor de contexto
- `CLAUDE.md` reducido de ~75 a ~38 lineas. Solo contiene: identidad del repo, idioma, regla "no commits sin pedir", separacion fabrica vs cliente, comandos universales, indice de skills, puntero a memoryLTS.
- `AGENTS.md` eliminado del root.
- 6 skills creadas en `.claude/skills/`:
  - `arquitectura-fabrica/SKILL.md` — stack, estructura, RSC, reglas TS/Tailwind, performance.
  - `wordpress-bridge/SKILL.md` — plugin propio, bridge-fields.json, naming GraphQL, codegen, problemas conocidos.
  - `data-layer/SKILL.md` — lib/wordpress, queries, fetchers tipados, Zod en repeaters, /api/revalidate.
  - `i18n-fabrica/SKILL.md` — next-intl, layouts, namespaces, patron labels delegadas.
  - `replicacion-cliente/SKILL.md` — checklist Fase 1-4 para levantar un cliente nuevo, reglas de oro.
  - `diseno-fabrica/SKILL.md` — design tokens, layout, section blueprint, tipografia, animaciones, componentes, a11y, globals.css, checklist premium. **Incluye bloque obligatorio que exige consultar `.claude/skills/taste-design/` antes de proponer UI nueva.**
- `.claude/agents/README.md` con esqueleto de subagente (YAML frontmatter `name`/`description`/`tools`/`model`). Catalogo vacio porque no hay workflows que justifiquen subagentes especulativos.

### Fase 3 — Sistema de memoria LTS
- Creado directorio `memoryLTS/`.
- `memoryLTS/memory.md` indice cronologico con descripciones <=140 chars.
- `memoryLTS/memory_2026-05-13-1.md` (este archivo) documentando el refactor.
- `.claude/skills/save-session-memory/SKILL.md` — comando `/save-session-memory` que automatiza la creacion del siguiente snapshot y el update del indice.

### Fase 4 — Verificacion
- `tasks.md` marcado al completar cada paso.
- Sin cambios en `app/`, `components/`, `lib/`, `wordpress/plugins/` ni en archivos de cliente.
- `npx tsc --noEmit` y `npm run lint` no tocados (refactor 100% documental).

## Decisiones tomadas

- **Una skill por dominio funcional, no por tema academico.** El contenido se agrupa por *cuando se necesita*, no por *de que tipo es*. Asi cargar una skill carga 100% de lo necesario para esa tarea y 0% de lo que no.
- **`diseno-fabrica` exige `taste-design/` explicitamente.** Las reglas mecanicas (paddings, easing) son "el suelo"; `taste-design/` es "el techo". Sin enforcement, las reglas mecanicas producen consistencia generica.
- **Cortina Studio NO aparece como regla en ninguna skill global.** Aparece solo como ejemplo concreto cuando es util, siempre prefijado con "caso Cortina Studio: ...". Las reglas estan en abstracto.
- **`.claude/agents/` queda vacio (solo README).** No se inventan subagentes especulativos. Se materializan cuando un workflow real lo justifica.
- **memoryLTS con indice tweet-size.** El indice se escanea de un vistazo; los archivos individuales solo se leen si la descripcion sugiere relevancia.
- **`AGENTS.md` se elimina, no se mantiene como duplicado.** Si en el futuro se necesita un equivalente para otros runners, se genera por composicion automatica de las skills.

## Pendientes / siguientes pasos

- Validar en proxima sesion que la carga selectiva de skills realmente reduce el contexto consumido (estimado: ~70% en tareas que no tocan diseno o WP).
- Cuando aparezca el primer subagente concreto (probable candidato: validador de mirror entre `bridge-fields.json` y `wp-config.json.fields`), crearlo en `.claude/agents/` siguiendo el esqueleto.
- Continuar con Fases 3 y 4 del proyecto Cortina Studio (queries .graphql + fetchers tipados → conexion en componentes).
