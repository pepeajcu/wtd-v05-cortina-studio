# Sesion 2026-05-18 #1 — Refactor Tier A/B/C: copy estatico a JSON, fabrica de 1-3h

## Contexto previo

Cortina Studio venia con un modelo de "todo a WordPress": ~35 meta fields en JetEngine cubriendo tanto datos operativos (Tier B) como copy estatico (hero/problems/reels/process titulares, eyebrows, CTAs, microcopy). El setup por cliente era pesado y, al revisar el codigo, salio un hallazgo critico: los componentes leian copy desde WP **a pesar** de que `messages/{es,en}.json` ya tenia esos mismos textos. Resultado: el i18n no funcionaba en `/en/` (mostraba espanol porque WP es monolingue). Conversacion estrategica con el usuario apunto a una fabrica replicable en 1-3h por sitio; el modelo actual lo impedia.

## Que se hizo

- Conversacion estrategica: definicion del marco de 3 tiers (A: copy en JSON i18n, B: datos operativos en WP Options, C: contenido dinamico en WP CPTs).
- Inventario completo de los 41 campos de `bridge-fields.json` + descubrimiento de la duplicacion entre WP y JSON.
- Enriquecimiento de `messages/es.json` y `messages/en.json` con Tier A completo (brand.name, hero, problems con cards, reels, process con rotating_words como array y steps).
- Adelgazamiento de `lib/graphql/queries/getHome.graphql` (de 22 campos a 3) y `getGeneral.graphql` (de 14 campos a 8).
- Reescritura de fetchers `getHome.ts` y `getGeneral.ts` con tipos drasticamente reducidos.
- Refactor de 4 componentes de seccion: `Hero` (client, `useTranslations`), `ProblemsSection`/`ProcessSection`/`ReelsSection` (RSC, `getTranslations`). Constantes estructurales (PROBLEM_CARDS, PROCESS_STEPS) viven como `const` local con key+icon.
- Actualizacion de `app/[locale]/page.tsx`: ya no pasa copy a componentes, solo datos Tier B/C.
- Adelgazamiento de `bridge-fields.json` (41 → 11 campos) y `wp-config.json` (sin iconMap; solo Tier B/C fields). Actualizacion de `lib/wordpress/config.ts` para que el schema Zod no exija el iconMap eliminado. Ajuste del comentario en `lib/iconMap.tsx`.
- Verificacion: `npx tsc --noEmit` y `npm run lint` verdes.
- Creacion de `recursos/LIMPIEZA_WP_CORTINA.md` con la lista accionable exacta de campos a borrar en JetEngine.
- Actualizacion de 5 skills con el marco de 3 tiers: `arquitectura-fabrica` (nueva seccion 7), `replicacion-cliente` (tabla + checklist + estado Cortina), `data-layer` (ejemplos query/fetcher + seccion tier-based), `wordpress-bridge` (bridge-fields.json minimo de referencia), `i18n-fabrica` (nueva seccion 8 sobre frontera con WP).
- Sincronizacion `.claude/skills/` ↔ `.opencode/skills/` (5 archivos), verificada con `Compare-Object`.

## Decisiones tomadas

- **Modelo de 3 tiers como contrato del motor.** Regla de decision: "el cliente lo edita mas de 2 veces al ano" → Tier C (CPT). "Dato operativo puntual" → Tier B (Options). "Texto que casi nunca cambia" → Tier A (JSON). Razon: para una fabrica de 1-3h por sitio, el setup WP debe ser minimo; el cliente no necesita poder editar copy del hero.
- **`hero_image_caption` se queda en WP (monolingue por ahora).** Razon: esta acoplada a la imagen que cambia el cliente; si el caption en `/en/` se ve raro, se mueve a JSON luego. Trade-off explicito y acotado.
- **`nav_items` va a JSON (Opcion B), no a CPT.** Razon: el header de un sitio premium no cambia con frecuencia; el dev edita JSON cuando aplique. Si un cliente especifico exige editar nav desde WP, se escala a CPT con `label_es`/`label_en` (Opcion A) solo para ese cliente — politica explicita "default JSON, escalar solo cuando se pida".
- **`process.rotating_words` pasa de string codificado (`hogar:m,...`) a array tipado de objetos `{text, gender}` en JSON.** Razon: legible, validable con Zod, alineado con el shape que ya esperaba `ProcessTitle`.
- **Constantes estructurales (PROBLEM_CARDS, PROCESS_STEPS) viven en el componente, no en WP ni en JSON.** Son codigo cliente-especifico (qué cards renderizar y con qué icono). El copy esta en JSON, la estructura en el componente.
- **No correr codegen en el repo durante el refactor.** Razon: los tipos generados actuales son superset (incluyen campos que WP todavia expone). tsc valida sin problemas. El usuario correra codegen DESPUES de borrar los campos en JetEngine, para que el schema regenerado refleje solo Tier B/C.
- **Banner explicito en `replicacion-cliente`**: el copy ya no se sube a WP. La columna izquierda de archivos por cliente ahora prioriza `messages/{es,en}.json` como segundo paso despues del brief.
