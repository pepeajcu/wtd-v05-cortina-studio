# Sesion 2026-05-16 #2 — Fase 4: Migracion del Home a WordPress datos reales

## Contexto previo

Fase 3 cerrada al 2026-05-16 #1: los 3 fetchers (`getHome`, `getProyectos`, `getGeneral`) retornaban datos validados con Zod, pero el Home (`app/[locale]/page.tsx`) seguia renderizando arrays hardcodeados (`REELS`, `PROBLEMS`, `STEPS`) y un `502XXXXXXXX` literal en 3 sitios. Fase 4 = migrar el Home a RSC + secciones por props desde WP. La fase la planificamos punto por punto, con confirmacion del usuario en cada salto.

## Que se hizo

- Creado `lib/iconMap.tsx` — registry unificado de iconos del motor (acepta tanto Lucide names directos como `Thermometer` para problems, como slugs como `whatsapp`/`mappin` para process). `WhatsAppIcon` extraido del inline de `ProcessSection`. Fallback `HelpCircle` con `console.warn` en dev.
- Agregado `databaseId: Int` a `getProyectos.graphql` + codegen + `ProyectoData`. Habilita el match con `home.reels.selected.id` (que viene como string numerico).
- Convertido `app/[locale]/page.tsx` a RSC: `Promise.all([getHome, getProyectos, getGeneral, getMediaUrls])`. Filtra proyectos por orden del repeater. Warn de IDs huerfanos.
- Migradas las 4 secciones (`Hero`, `ProblemsSection`, `ReelsSection`, `ProcessSection`) a recibir props derivadas de `HomeData[seccion]`. WhatsApp number ya no es literal, viene de `general.whatsappNumber`.
- Bug encontrado durante validacion visual: el bridge devuelve **attachment IDs crudos** para campos Media de JetEngine (ej. `video: "16"`). Workaround: nuevo fetcher `lib/wordpress/getMediaUrls.ts` + query `getMediaUrls.graphql` que resuelve IDs a URLs via `mediaItems(where: { in: $ids })`.
- Bug-dentro-del-bug: la primera version usaba `sourceUrl`, que WPGraphQL solo popula para imagenes; para videos hay que usar `mediaItemUrl`. Fix: el fetcher pide ambos y cae primero en `mediaItemUrl`.
- Cleanup colateral necesario para que pasara `next build`: removidos imports muertos en `components/ui/ReelCard.tsx` (`Link`, `motion`, `AnimatePresence`, `Instagram`, `Music2`) y typeo de `ease: [..] as any` → tupla `[number, number, number, number]` en `FadeInStagger.tsx`.
- Eliminado `app/api/debug/fetchers/` (route handler temporal de Fase 3, ya cumplio su rol diagnostico).
- Agregado tag `wp:media` a `lib/wordpress/tags.ts` para cache de attachments.
- Marcados todos los bullets de Fase 4 en `docs/specs/001-plan-inicial/task.md`, dejando solo el bullet del webhook end-to-end como `[~]` (parcialmente validado en dev).

## Decisiones tomadas

- **Workaround frontend para attachments en vez de tocar el plugin PHP.** Decision del usuario tras presentarle 3 opciones. Trade-off: 1 query GraphQL extra por request del Home a cambio de no tocar el bridge ni redeployar el plugin. La mejora arquitectonica (agregar tipo `"media"` al plugin para que el bridge resuelva en server) queda pendiente como follow-up de plugin.
- **`IconComponent = ComponentType<any>` con eslint-disable explicito** en `iconMap.tsx`. Razon: Lucide expone `ForwardRefExoticComponent` con `strokeWidth: string | number`, incompatible a nivel de tipo con un `WhatsAppIcon` casero. El codebase ya usa el mismo patron en `FadeInStagger`/`ProblemsSection`/`ProcessSection`, asi que aqui es coherente. Disable documentado con comment explicando el por que.
- **No tocar `messages/{es,en}.json`** (decision del usuario). El codigo migrado deja huerfanas las claves de hero/problems/reels/process en los JSON, pero facilita un revert rapido. Limpieza queda como follow-up tras validacion definitiva.
- **Filtrado silencioso de IDs huerfanos en `reels.selected`** con `console.warn` server-side. Razon: un proyecto borrado en WP no debe romper el render del Home; el aviso queda en logs.
- **Match `reels.selected` ↔ `proyectos` por `databaseId` numerico** (no por slug). El selector de JetEngine guarda IDs; el slug requeriria cambio en CMS y otra ronda de redis del usuario.
- **WhatsApp del Process usa `general.whatsappDefaultMessage`** (Hero y Reels tienen sus propios `ctaMessage`/`whatsappMessage` en el Home singleton; Process no tiene campo dedicado en el schema).
- **El bullet del webhook end-to-end se valida en Fase 5** (no en Fase 4). Razon: en `next dev` no hay cache persistente, asi que el refresh refleja cambios sin necesidad de webhook. La prueba estricta del `revalidateTag` solo aplica a `next start`/deploy y requiere tunel o deploy real. El usuario confirmo que el refresh funciona en dev — eso valida el codigo, no la infra.

## Pendientes / siguientes pasos

- **Fase 5 (proximo bloque):** prueba end-to-end del webhook contra `next start` con tunel/deploy. Esta es la unica validacion que falta de Fase 4 a nivel estricto.
- **Mejora arquitectonica del plugin bridge:** agregar soporte para tipo `"media"` en `bridge-fields.json`. El resolver llamaria `wp_get_attachment_url($meta_value)`. Eliminaria el fetcher `getMediaUrls` y la segunda query GraphQL por Home. Mover `video`, `video_poster`, `hero_image`, `brand_logo` a esa categoria. Trabajo del plugin, no del motor.
- **Limpieza de `messages/{es,en}.json`:** despues de Fase 5 validada, remover claves migradas a WP (`hero.*`, `problems.*`, `reels.*`, `process.*`). Mantener solo UI labels (`projectCard.*`, `nav.*`, `common.*`, `footer.*`).
- **Brand logo y otros campos Media de `general`:** actualmente `general.brand.logo` no se consume en ninguna seccion. Cuando se conecte (footer, header), aplicar la misma resolucion via `getMediaUrls`.
